# ADR 0001: Adapter-first App Router integration

- Status: Accepted
- Date: 2026-07-16
- Decision owners: project owner and NextJsHx maintainers
- Related Beads: `nxhx-f34.1.3` (`NXHX-F03`)
- Related PRD sections: 9, 14, 16

## Context

Next.js App Router modules are contracts expressed simultaneously through the
filesystem, ECMAScript module shape, directive placement, and TypeScript types.
These dimensions are independently meaningful:

1. Pages and layouts are discovered at exact special paths and default-export
   components. Route Handlers use named HTTP method exports.
2. Client and server boundaries use directive prologues whose placement changes
   module meaning.
3. Route-aware helpers generated by Next provide a second type oracle for page,
   layout, and handler signatures.
4. App Router directories normally mix route modules with native components,
   styles, tests, assets, and third-party code.

The current Next.js documentation reflects these constraints:

- [`page.tsx`](https://nextjs.org/docs/app/api-reference/file-conventions/page)
  default-exports the route component and can use the generated `PageProps`
  helper.
- [`layout.tsx`](https://nextjs.org/docs/app/api-reference/file-conventions/layout)
  default-exports a layout and can use the generated `LayoutProps` helper.
- [`route.ts`](https://nextjs.org/docs/app/api-reference/file-conventions/route)
  exposes supported HTTP methods as named exports and can use `RouteContext`.
- [`use client`](https://nextjs.org/docs/app/api-reference/directives/use-client)
  must be at the top of a boundary module before imports.
- [`use server`](https://nextjs.org/docs/app/api-reference/directives/use-server)
  applies at the top of a server-function module or at the beginning of a
  function body.

genes-ts emits strict split ESM TypeScript/TSX with a file per Haxe module. That
is a good implementation-module shape, but a Haxe type does not naturally
become an arbitrarily placed `app/**/page.tsx`, a default function export, a set
of named HTTP exports, or a directive prologue before generated imports.

The integration strategy must preserve all of the following:

- ordinary Next.js project structure and runtime behavior;
- typed Haxe source and strict generated TypeScript;
- readable output that a Next.js developer can inspect;
- mixed Haxe/native ownership at individual-file granularity;
- generic genes-ts evolution rather than a Next-specific compiler fork;
- fail-closed generation, collision handling, and cleanup.

## Decision

### Adapter-first generation is canonical

NextJsHx will use narrow generated TypeScript/TSX adapters as the canonical
bridge between genes-ts implementation modules and Next.js convention modules.

The canonical pipeline is:

```text
Haxe declaration
  → Haxe macro validation
  → deterministic adapter intent
  → genes-ts implementation module
  → validated and formatted Next-native adapter
  → transactional manifest-owned publication
  → next typegen
  → strict TypeScript
  → next build
```

The Haxe source remains the behavior source of truth. The genes-ts module
contains the implementation. The adapter contains only the minimum convention
surface that Next.js requires.

### Adapter responsibilities

An adapter may:

- select an exact project-relative target such as
  `src/app/todos/[id]/page.tsx`;
- emit an allowed module or function directive in deterministic order;
- import a precisely named genes-ts implementation value;
- expose the required default export;
- expose reviewed named exports such as an HTTP method, metadata function, or
  literal segment configuration;
- wrap the implementation with an explicit public signature using supported
  Next or platform types;
- carry a concise generated-source header used for diagnosis, never as proof of
  ownership.

An adapter must not:

- contain application business logic;
- decode arbitrary data through broad casts or unchecked field access;
- duplicate route declarations in a central runtime registry;
- implement routing, rendering, caching, Server Functions, or React boundaries
  outside native Next/React semantics;
- import unsupported `next/dist/**` runtime modules;
- infer ownership from its path, header, directory, or generated appearance;
- merge with an existing native module.

Wrappers with explicit signatures are preferred over broad re-exports when a
wrapper lets Next's own types validate the public contract.

### Representative adapter shapes

A page adapter gives the exact route file a default export and retains Next's
route-aware type check:

```tsx
// Generated by NextJsHx. Source: app.routes.TodoPage. Do not edit.
import { TodoPage } from "../../../../src-gen/app/routes/TodoPage";

export const revalidate = 60;

export default function Page(props: PageProps<"/todos/[id]">) {
  return TodoPage.render(props);
}
```

A client boundary places the directive before every import:

```tsx
"use client";

// Generated by NextJsHx. Source: app.components.TodoToggle. Do not edit.
import { TodoToggle } from "../../../src-gen/app/components/TodoToggle";

export default TodoToggle.render;
```

A Server Function boundary exposes only reviewed async functions:

```ts
"use server";

// Generated by NextJsHx. Source: app.actions.TodoActions. Do not edit.
import { TodoActions } from "../../../src-gen/app/actions/TodoActions";

export async function createTodo(formData: FormData) {
  return TodoActions.createTodo(formData);
}
```

A Route Handler maps Haxe methods to the exact named exports consumed by Next:

```ts
// Generated by NextJsHx. Source: app.api.TodosRoute. Do not edit.
import { TodosRoute } from "../../../../src-gen/app/api/TodosRoute";

export function GET(
  request: Request,
  context: RouteContext<"/api/todos/[id]">
) {
  return TodosRoute.get(request, context);
}

export function DELETE(
  request: Request,
  context: RouteContext<"/api/todos/[id]">
) {
  return TodosRoute.delete(request, context);
}
```

These are contract examples, not a lock on the F04 Haxe authoring syntax.

### Deterministic intent before file writes

Build macros register adapter intent; they do not directly mutate the App Router
tree. An intent must retain enough information to validate and diagnose the
planned publication:

- schema version and adapter kind;
- Haxe source type, field, and source position;
- target path relative to the discovered App Router root;
- exact imports and implementation symbols;
- ordered directives;
- default and named exports;
- public TypeScript signature strategy;
- selected Next and genes-ts identities;
- ownership and collision expectations.

The complete plan is sorted and validated before rendering. Duplicate targets,
unsupported adapter kinds, malformed paths, conflicting directives or exports,
and known type mismatches fail before a live file is changed.

### Publication and ownership remain separate from rendering

Producing correct adapter bytes does not prove permission to write them.
Publication must:

1. canonicalize the project and output roots;
2. reject absolute paths, traversal, reserved paths, symlink files, and symlink
   escapes;
3. validate the previous manifest and verify every existing owned digest;
4. reject every existing target that lacks verified manifest ownership;
5. render the complete next adapter tree in staging;
6. format and syntax-check all staged outputs;
7. journal the prior and intended states;
8. publish changed files and remove stale verified files;
9. replace the manifest last;
10. run `next typegen`, strict TypeScript, and the relevant Next build check;
11. restore the prior adapter state if post-publication validation fails.

No directory is wholly owned. Two special files in the same route segment may
have different owners.

### Files NextJsHx never owns implicitly

NextJsHx never implicitly owns or rewrites:

- `.next/**`;
- `next-env.d.ts`;
- `node_modules/**`;
- package-manager lockfiles;
- `package.json` or workspace manifests;
- `next.config.*`;
- `tsconfig*.json`;
- native App Router modules absent from the ownership manifest;
- native components, styles, tests, or assets colocated with generated routes;
- `public/**`;
- deployment and hosting configuration;
- environment files or credentials;
- genes-ts output merely because the same command orchestrated its build.

Initialization may propose a separately reviewed, idempotent patch to an
app-owned configuration file. Such a patch is not adapter ownership and must
remain independently diffable. A missing or invalid ownership manifest means
NextJsHx owns no live adapter.

### Validation is layered

No single checker is treated as sufficient:

- Haxe checks the author-facing declaration and supported semantic contract.
- The adapter renderer checks path, directive, export, and signature structure.
- The ownership publisher checks permission and transaction safety.
- `next typegen` produces route-aware Next types.
- strict TypeScript checks adapter and implementation interoperability.
- `next build` checks the real framework/compiler/bundler integration.
- focused runtime or browser tests check behavior where static evidence is
  insufficient.

TypeScript and Next errors remain blocking. NextJsHx must not insert `any`,
unchecked casts, suppression comments, or disabled Next build checks to make an
adapter pass.

### Direct-emission admission criteria

Direct genes-ts emission may replace a specific adapter kind only through a
reviewed superseding or amending ADR. Every affected kind must independently
satisfy all of these conditions:

1. The genes-ts capability is generic—such as directives, export metadata, or
   import forms—and contains no Next route or framework-specific concept.
2. The emitted module has the exact target path, directive placement, export
   shape, and public signature required by the selected Next version.
3. Output is at least as short, deterministic, readable, and snapshot-testable
   as the adapter it replaces.
4. The route-aware Next type oracle remains present; direct emission does not
   weaken `PageProps`, `LayoutProps`, `RouteContext`, or equivalent checks.
5. DCE and module-graph reachability are proven for both Haxe-authored and
   TypeScript-authored consumers.
6. The generic compiler change passes the complete genes-ts TypeScript and
   classic-JS suites.
7. The stable Next fixture passes type generation, strict TypeScript, build,
   and focused runtime evidence with byte-level generated-output snapshots.
8. Mixed native/Haxe ownership, collision detection, transactional publication,
   repair, and clean semantics remain unchanged.
9. Migration is deterministic and does not switch output strategy implicitly
   based on local checkout state, tool availability, or canary detection.
10. No broad cast, suppression, hidden runtime, or Next-specific compiler fork
    is introduced.

Even when genes-ts directly renders convention-module contents, the NextJsHx
plan and publisher remain responsible for target selection and proven file
ownership. Direct emission is a simplification of bytes, not permission to
bypass publication controls.

## Consequences

Positive consequences:

- Next.js receives ordinary, recognizable App Router modules.
- genes-ts stays framework-independent.
- Haxe and Next/TypeScript provide complementary type checks.
- Directives and exports are visible in small files rather than hidden in a
  custom runtime.
- Existing native routes can coexist at file granularity.
- Generated writes can be audited, rolled back, repaired, and cleaned by exact
  manifest evidence.
- Future compiler improvements can remove redundant adapters incrementally
  without changing the architecture's safety boundary.

Costs and constraints:

- The repository contains an additional generated layer.
- Diagnostics must preserve Haxe source positions across plan, implementation,
  and adapter output.
- Relative imports and file movement require deterministic regeneration.
- Adapter snapshots, ownership tests, strict TypeScript, and real Next builds
  are mandatory maintenance costs.
- A compiler feature that looks more elegant is insufficient by itself; it must
  meet the direct-emission admission criteria.

The adapters add no application runtime protocol. They are ordinary modules
consumed and optimized by Next.js.

## Rejected alternatives

### Generic direct compiler emission as the initial integration

Generic directive and export support is desirable, but it does not by itself
solve arbitrary App Router target paths, file-level ownership, collisions,
transactional publication, or the use of Next-generated route-aware signatures.
Making it the initial requirement would couple foundation progress to a broader
compiler program and invite Next-specific behavior into genes-ts.

Direct emission remains an admitted future optimization under the criteria
above; it is rejected only as the unconditional initial strategy.

### A custom runtime or router

A custom runtime or router would duplicate Next.js behavior, obscure React
Server Components and Server Function semantics, complicate deployment, and
drift from the framework's compiler and bundler. It contradicts the product
requirement that the output remain an ordinary Next.js application.

### Hand-maintained adapters

Hand-maintained adapters can prove an early integration fixture, but they are
not the product architecture. They duplicate paths, directives, exports, and
signatures; can drift from Haxe declarations; provide no reliable cleanup or
ownership evidence; and do not scale to route changes. F05 may use one
hand-written adapter as a deliberately temporary proof before the generator
exists.

### Externs without an adapter layer

Faithful externs expose callable Next APIs but cannot materialize filesystem
conventions, directive boundaries, default exports, or collision-safe generated
files. Externs are necessary for raw bindings and insufficient for App Router
authoring.

## Scope not decided here

This ADR does not select:

- the public `nextjs.*` annotation or macro syntax;
- the complete route metadata model;
- the ownership manifest's final JSON schema;
- the CLI implementation language;
- which future genes-ts directive/export capabilities will be accepted;
- support for every Next special file, Pages Router, or Edge Runtime.

Those decisions remain owned by their linked Beads and future ADRs.

## Change process

Evidence that a different strategy is better must identify the adapter kind,
show the exact generated diff, satisfy the validation and ownership obligations,
and link the relevant genes-ts and Next fixture results. Change this accepted
contract with a superseding ADR; do not silently switch generation strategy in
compiler flags, local configuration, or canary-only code.
